# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

The Crafty Cornerr — a marketing/storefront website for a handmade Indian home décor brand (wooden rangoli, pearl/stone rangoli, toran & borders, diyas, decorative flowers). The site itself is still a no-build, no-framework static `index.html` (HTML + CSS + JS in one file, plus one sibling ES module `ganpati-scene.js` for the Ganpati theme cinematic), but **product content now comes from a Sanity CMS** so the client can add products / change prices / upload photos without touching code. There is still no bundler or backend for the site; the `studio/` folder is a separate Node project (the CMS editor) that is *not* deployed with the site. The **folder** (minus `studio/`) is the deployable unit.

Sibling assets referenced by `index.html`: `loader.mp4` (intro loader video), `hero-doorway.jpg` (mobile hero background), `testimonial-illustration.png` (the "loved" section), theme hero artwork (`diwali-hero-bg.jpg`/`diwali-hero-mobile.jpg`, `ganpati-hero-bg.jpg`/`ganpati-hero-mobile.jpg`), and `ganpati-scene.js` + `ganesha-art.png` + `ganpati-scene-bg.jpg` (the Ganpati cinematic and its mandap backdrop). `support.html` is a standalone second page (support center: FAQ / shipping / exchange / contact) linked from the footer via `support.html` + `#faq`/`#exchange`/`#contact` anchors. These must ship alongside `index.html`. (Unreferenced source artwork that used to sit in the folder root was moved to the Trash on 2026-07-15 — every image now in the root is deployed.) Product photos load from Sanity's CDN at runtime (base64 product images were removed — the file dropped from ~3.7 MB to ~0.5 MB).

**Content editing / CMS:** see [studio/README.md](studio/README.md). The site works without Sanity configured (shows built-in starter text), but shows no product photos until a Sanity `projectId` is set in `studio/sanity.config.ts`, `studio/sanity.cli.ts`, and the `SANITY` block in `index.html`, and the one-time import has run. **This is already done** — project `c8746siu`, dataset `production`, import run, read token pasted in. Treat those three spots as one value that must stay in sync.

## Running / previewing

- **Preview:** use **`netlify dev`** — since the catalogue is fetched from a Netlify function, `file://` and `python3 -m http.server` cannot load products and the page falls back to built-in starter copy with no product photos. That fallback is by design (a dead endpoint degrades the page rather than breaking it), but it means a plain static server is no longer a faithful preview.
- **Deploy: `git push` to `main`. Do NOT run `netlify deploy` from this folder.**
  - The live site is **`thecraftycornerr.com`**, owned by the **client's** Netlify team (`magnus realtorsmktg`), building from `git remote origin` = `github.com/magnusrealtorsmktg-coder/craftycornerr`. Pushing to `main` is the only deploy path.
  - **`.netlify/state.json` points somewhere else** — at `9d1807a6-e9c1-48d0-a48f-2f3dd681c8ff`, a stale `the-crafty-cornerr` site on the *developer's* personal Netlify team. `netlify deploy --prod` would publish there, not to the client's live domain, and `netlify env:list` reports that site's (empty) variables. **The client's env vars cannot be inspected from this machine** — the developer's CLI login has no access to their team, so a "no environment variables set" result here proves nothing about production. Verify env vars in the client's Netlify UI instead.
  - `netlify.toml` runs `netlify-build.sh`, which `rsync`s the repo root into `dist/` **minus** `studio/`, `netlify/`, `node_modules`, `*.md` and local config, then publishes `dist/` with `netlify/functions` as the function dir. **Adding a new image or page to the repo root ships it automatically** — no list to update; the script works by exclusion. Never publish the repo root directly (it would serve `studio/` and its `node_modules`).
- **No tests, no lint, no build** for the site. Editing means editing the HTML file(s) and reloading the browser. There is nothing to run to "check" a change — verify in a browser.
- Commands, all of them:

  | Where | Command | What |
  |---|---|---|
  | root | `python3 -m http.server 8000` | faithful local preview |
  | root | `bash netlify-build.sh` | assemble `dist/` exactly as Netlify will |
  | root | `netlify deploy --prod` | deploy (runs the build above) |
  | `studio/` | `npm run dev` | Sanity Studio at :3333 |
  | `studio/` | `npm run deploy` | publish the Studio for the client |
  | `studio/` | `npm run extract-seed` / `npm run import` | the one-time seed import (already run) |

- `?theme=diwali` / `?theme=ganpati` on the URL overrides the CMS theme for local preview without touching Sanity.
- Third-party libs (GSAP + ScrollTrigger, Lenis smooth scroll) and Google Fonts load from CDN, so the first load needs internet.

## Architecture (all inside `index.html`)

Everything is in one file with three regions: `<style>` (top), the page markup (`<body>`), and one `<script>` (bottom) — except the Ganpati cinematic, which is the separate module `ganpati-scene.js`. Key ideas:

- **Data-driven rendering.** Sections are empty container elements (`#collgrid`, `#board`, `#occgrid`, `#steps`, `#reviewTrack`, `#cards`) that JS fills at runtime from data objects. To change products/copy, edit the data — not the markup.
  - `CATALOG` — the runtime source of truth for all products, keyed by category (`peacock`, `floral`, `corner`, `border`, `diya`, `flowers`). Each category has `{title, ek, products:[...]}`; each product has `id`, `name`, `price`, `old`, `badge`, `rating`, `rc`, `img`, `desc`, `specs`, `reviews`. It's declared with `let` because the Sanity loader reassigns it (see below). The literal in the file is now just a small **built-in starter/fallback** (text only).
  - `PIMG` — product image URLs keyed by product id (e.g. `pk1`, `fr2`). **No longer base64** — starts empty (`let PIMG={}`) and is filled at runtime with Sanity CDN URLs. A product's `img` field is the same URL; elements with `data-pimg="<key>"` get their `src` from `PIMG`. (Brand logo: `LOGO`/`NAV_LOGO` now point at the sibling file `logo.png` — a transparent-background PNG used in the nav badge (`.nav-brand`) and footer (`.foot-logo`); it must ship with the site. The old inline-base64 logo blobs were removed, dropping `index.html` from ~580 KB to ~160 KB.)
  - Parallel per-category style maps must be kept in sync with `CATALOG`'s keys: `GLOW`/`GLOW2` (card glow), `CATBG` (category background color). Adding a category means adding entries to all of these.
  - `ART` — inline SVG generators (`data-art` elements) for decorative category motifs; helpers `petalRing`/`dotRing`/`mark` build the SVG paths.

- **Products come from Sanity CMS, via our own endpoint — never Sanity directly.** `loadSanity()`/`bootCatalog()` GET [netlify/functions/catalog.mjs](netlify/functions/catalog.mjs) and rebuild `CATALOG`/`PIMG`/`COVER`/`SETTINGS` from `{categories, settings}`.
  - **Why the proxy:** this project's documents are genuinely private — an anonymous query returns **0 categories and 2 of 25 products**, so a token is required to read the catalogue at all. A token in `index.html` is public the instant anyone opens devtools, and it was committed to what is now a **public** repo (GitGuardian flagged it on 2026-08-25). The token now lives only in Netlify's env and is attached server-side. **Never reintroduce a `SANITY.token` in `index.html`.**
  - The response is edge-cached (`max-age=60, stale-while-revalidate=3600`), so it costs one Sanity round-trip per cache period, not one per visitor, and a Sanity outage serves the stale copy rather than blanking the shop. `bootCatalog()` (called after all data arrays, before the GSAP block) no-ops the CMS path until `projectId` is set (`sanityOn()`); when unset it renders built-in data synchronously (so ScrollTrigger sees the `.rv` elements). When set, it awaits Sanity then calls `renderAll()` + `revealSections()`.
  - **Rendering is deferred, not patched.** `renderAll()` re-runs every product-image section (`renderCollections`/`renderBoard`/`renderOccasions`/`fillPImages`/`renderHero`, then `applyTheme`/`syncHearts`) **once, after** data is ready — this avoids a broken-image flash and keeps the built-in `CATALOG` (image-less) purely as a fallback. Because those sections are (re)rendered *after* the ScrollTrigger `.rv` setup ran, `revealSections()` force-shows `#collgrid/#board/#occgrid .rv` (gated on `window.__revealReady`). The `.rv` reveal starts at `opacity:0`; anything rendered after ScrollTrigger setup must be force-shown or it stays invisible.
  - **Hero** cards + mobile background come from a singleton `siteSettings` doc (`heroProducts` references + `heroBackground` image); `renderHero()` overwrites the static `#cards .pincard` img/price/name and `.mhero-bg` src, falling back to the built-in `[data-pimg]` images when unset.
  - **Theme** (`siteSettings.theme`: `diwali` or `ganpati`) is applied by `applyTheme()` as `data-theme` on `<html>` (a `?theme=` URL param overrides for local preview). The resolved CMS theme is cached in `localStorage('tcc.theme')` and re-applied by a tiny inline `<head>` script **before first paint**, so a returning visitor doesn't flash the default skin while Sanity loads. `applyTheme()` dispatches a `themechange` CustomEvent — theme-gated features (both cinematics, the typewriter) listen for it because the theme usually lands *after* their setup ran. Each theme is a full festive skin scoped to `[data-theme=…]`: it **overrides the `:root` palette variables**, restyles CTAs/nav, and swaps the hero backgrounds to its `*-hero-bg.jpg`/`*-hero-mobile.jpg` artwork. A typewriter reveal on the hero "kick"/`.mhero-label` runs for any non-default theme (waits for the `intro:done` loader event; skipped under reduced-motion).
  - **Diwali cinematic** (`#dwFx`): a diya ignites → gold/champagne/saffron fireworks → sparkles + marigold petals → gentle fade. Single-canvas, pre-rendered-sprite, additive-glow particle system (one rAF loop, stops after ~4.3 s) that plays **once per load** when scrolled past the hero; gated on `data-theme==="diwali"`, skipped under reduced-motion, `pointer-events:none`, z-index below the nav.
  - **Ganpati cinematic** (`#gnScene`, a full-viewport `.gn-scene` section right after the hero, `display:none` outside the theme): GPU particles form ॐ, then Ganesha, in [ganpati-scene.js](ganpati-scene.js) — the only JS outside `index.html`. The stage is the `ganpati-scene-bg.jpg` mandap artwork (CSS background, light cream centre); the canvas is transparent and the particles are **dark kumkum tones with normal blending** so they read on the light backdrop — don't switch to additive/glow colours without also darkening the stage. A **cloud wipe** (`#cloudWipe`, fixed overlay at z-150, under the nav) hides the hero→mandap background cut: JS-built white puffs + a veil are swept over the viewport by a scrubbed ScrollTrigger while `#gnScene` enters; Ganpati theme only, skipped under reduced-motion. Three.js + GLSL + UnrealBloom, resolved via an **importmap** in `<head>` (unpkg CDN) and dynamically `import`ed only when the theme is `ganpati` (`boot()` runs at load and on `themechange`, once). No textures/models: the ॐ glyph (Noto Serif Devanagari) and `ganesha-art.png` (built-in SVG silhouette fallback) are rasterised offscreen and their pixels sampled into per-particle targets. Renders only while on screen (IntersectionObserver); reduced-motion shows a static formed Bappa instead. Tunables live in the exported `CONFIG` at the top of the file.
  - **The custom-order enquiry form writes to Sanity, then emails.** `#customForm` POSTs JSON to [netlify/functions/submit-enquiry.mjs](netlify/functions/submit-enquiry.mjs), which creates an `enquiry` doc **first** (the durable copy) and then notifies the studio. It used to POST straight to Web3Forms, which left no record — a lead buried in Gmail was simply lost. The visitor only sees an error if *both* the write and the email fail. Spam is caught by a `botcheck` honeypot (`.cf-bot`); a bot that fills it gets a 200 so it learns nothing. On failure the typed values are deliberately left in the fields. The WhatsApp number (`917030924448`) appears in `index.html` and `support.html` — update both.
  - **All transactional email goes through Brevo** ([netlify/functions/lib/email.mjs](netlify/functions/lib/email.mjs)): studio packing slip, customer order confirmation, enquiry notification. **Web3Forms cannot be used server-side** — its free plan rejects non-browser requests (`"Use our API in client side"`), so the original Web3Forms call in `verify-payment` silently never sent. `sendMail()` logs and returns rather than throwing, so a missing `BREVO_API_KEY` costs a notification, never an order.
  - **Phone numbers are normalised, not just length-checked.** `normalisePhone()` exists in both [lib/shop.mjs](netlify/functions/lib/shop.mjs) (the gate) and `index.html` (instant feedback) — strip `+91`/leading `0`/punctuation, require `^[6-9]\d{9}$`, reject repeated-digit placeholders. Keep the two in step. Orders also store `verifiedPhone`, the contact Razorpay processed the payment with, as a cross-check.
  - **Reviews are moderated.** Each product's `reviews` merge its curated seed reviews with approved `review` documents (`approved==true`) via GROQ `+`. The PDP form POSTs to `netlify/functions/submit-review.mjs`, which writes a `review` doc with `approved:false` using a **server-only** `SANITY_WRITE_TOKEN` (Netlify env var, never in the site). The client approves in the Studio (pending/approved lists in the desk structure).
  - **Checkout is Razorpay, and the browser is never trusted with money.** Two functions, sharing [netlify/functions/lib/shop.mjs](netlify/functions/lib/shop.mjs) (in `lib/` so Netlify's function detector skips it):
    1. [create-order.mjs](netlify/functions/create-order.mjs) — receives only `[{id, qty}]` plus the delivery address. It **re-reads every price from Sanity** and recomputes subtotal/shipping/total (`priceCart()`), so a cart edited in devtools changes nothing. It then opens a Razorpay order and returns `RAZORPAY_KEY_ID` in the response — the key id is deliberately **not** hardcoded in `index.html`. A pending `order` doc is written first (fail-soft: a Sanity outage must not block a paying customer).
    2. [verify-payment.mjs](netlify/functions/verify-payment.mjs) — Razorpay's browser callback is forgeable, so the sale only counts once `verifySignature()` confirms the HMAC of `<order_id>|<payment_id>` against `RAZORPAY_KEY_SECRET`. Then it flips the order to `paid` and emails the studio a packing slip via Web3Forms. **Everything after the signature check is fail-soft** — the customer has already been charged, so a Sanity or email failure must never surface as a payment failure.
    - **The shipping rule exists twice on purpose**: `SHIPPING_FLAT`/`FREE_SHIPPING_OVER` in `lib/shop.mjs` is what gets **charged**; `SHIP_FLAT`/`SHIP_FREE_OVER` in `index.html` is what the cart **displays**. Change both together or the drawer total and the Razorpay total disagree. `support.html` quotes the same numbers in prose.
    - Front end: checkout is a third mode of the existing side drawer (`drawerMode` = `cart` | `fav` | `checkout` | `done`), so it inherits scroll-lock and transitions. `Store.onChange` deliberately **skips re-rendering** in `checkout`/`done` mode — otherwise a cart event would wipe a half-typed address or replace a paid receipt. `coDraft` persists typed values across re-renders. `checkout.js` is loaded lazily on the first Pay click, not at page load.
    - **Availability**: `product.available` in Sanity. Only an explicit `false` hides the buy button (docs predating the field have it `undefined`) — `buyable()` in `index.html` and `priceCart()` in `shop.mjs` implement the identical rule, and both must stay in step. Unavailable products still render, with "Temporarily unavailable" in place of the buy button; an item that sells out while in someone's bag disables checkout.
    - Orders land as `order` docs, split in the Studio desk into "to pack" / "shipped" / "all". Money and address fields are `readOnly` — they are written by the functions, never by hand; the client only changes `status` and `trackingNote`.
  - The editor lives in [studio/](studio/) (Sanity v3, **`.ts` config — do not add `"type":"module"`**, it breaks the CLI's config loader; a `tsconfig.json` must exist so the CLI doesn't walk up into `~/Desktop`). Schemas: `siteSettings`, `category` (`key`↔category keys), `product` (`code`↔`id`, specs as label/value, seed `reviews` inline), `review` (moderated). See [studio/README.md](studio/README.md) for full setup, the one-time import (`scripts/extract-seed.mjs`+`scripts/import.mjs`), CORS, and the `SANITY_WRITE_TOKEN` step. Studio commands run from `studio/`: `npm run dev` (localhost:3333), `npm run deploy` (publishes the editor to `the-crafty-cornerr.sanity.studio` for the client). `studio/` is never deployed with the site.

- **The shop is an overlay, not a page.** `#shopOv` is a fixed overlay with two inner views: `#catView` (category product grid) and `#pdpView` (product detail). `openCategory(key)` renders the grid, `openProduct(key,id)` renders the PDP, `closeShop()` dismisses. Navigation is in-DOM (toggling classes `open` / `in-pdp`); there is no router.
  - **Cart & favourites are real but local.** The `Store` IIFE persists both to `localStorage` (`tcc.cart`, `tcc.fav`) keyed as `"<catKey>:<productId>"`, and notifies subscribers via `Store.onChange`. `#drawer` is one slide-out shared by both modes (`openDrawer('cart'|'fav')`, `renderDrawer`), with nav count badges (`renderBadges`) and PDP heart sync (`syncHearts`). Items whose id no longer resolves in `CATALOG` are filtered out on read, so a product deleted in Sanity can't break a saved cart. **Checkout is the only stub** — it fires a `toast()`. Anything that reassigns `CATALOG` must re-run `syncHearts`/`renderBadges` (`renderAll()` does).

- **Motion layer (GSAP + Lenis).** At the bottom of the script: Lenis drives smooth scrolling and is wired into GSAP's ticker and `ScrollTrigger`. `lenis.stop()/start()` (via `lockScroll`) is used to freeze the page when overlays/mobile menu are open. Entrance animations use the `.rv` ("reveal") class + `ScrollTrigger`. Mouse parallax keys off `[data-d]` attributes (depth factor).

- **Accessibility / responsive gating.** Code branches on `matchMedia('(prefers-reduced-motion:reduce)')` (`reduced`) and `(max-width:820px)` (`small`) to disable Lenis, parallax, the marquee wall, and heavy animations. When adding motion, gate it the same way.

## Secrets & repo layout

- `.claude/` is **gitignored** (it holds a Sanity Editor token in `settings.local.json`), as are `.env`, `studio/.env`, `dist/`, `studio/seed/` and both `node_modules`.
- Two tokens with opposite rules: the **Viewer** token in `index.html`'s `SANITY` block is read-only and *meant* to ship; the **Editor** token `SANITY_WRITE_TOKEN` lives only in Netlify's env vars and must never appear in a shipped file. `submit-review.mjs` hardcodes its own `PROJECT`/`DATASET`/`API` constants and `lib/shop.mjs` exports its own — changing the Sanity project means editing both.
- **Netlify environment variables** (none of these are in the repo):

  | Variable | Used by | Without it |
  |---|---|---|
  | `RAZORPAY_KEY_ID` | both checkout functions | checkout returns 503 and points the customer at WhatsApp |
  | `RAZORPAY_KEY_SECRET` | both checkout functions | same — and no signature can be verified |
  | `SANITY_WRITE_TOKEN` | reviews, orders | `create-order` refuses to price the cart (503) rather than trust the browser; reviews silently drop |
  | `WEB3FORMS_KEY` | order notification email | falls back to the public key already in `index.html` |
  | `SANITY_READ_TOKEN` | `catalog` (optional) | falls back to `SANITY_WRITE_TOKEN`; if neither is set the shop shows no products |
  | `BREVO_API_KEY` | all order/enquiry email | nothing is emailed — orders still land in the Studio, but nobody is told |
  | `MAIL_FROM` | Brevo sender | defaults to `orders@thecraftycornerr.com`; the domain needs SPF/DKIM or mail goes to spam |
  | `STUDIO_EMAIL` | studio notifications | defaults to `thecraftycornerr26@gmail.com` |

  Set these in the **client's** Netlify project (`thecraftycornerr.com`), not the developer's — see the deploy note above for why `netlify env:list` cannot confirm them from this machine. `RAZORPAY_KEY_ID` has a test-mode fallback in `lib/shop.mjs` (the key id is public); the other three have none. **`create-order` refusing to run when `SANITY_WRITE_TOKEN` is missing is the correct behaviour** — it cannot verify prices against the catalogue, so it must not take money.

## Conventions

- **Brand colors are CSS variables** in `:root` at the top of `<style>` (`--cream`, `--peach`, `--coral`, `--sage`, `--lav`, `--charcoal`). Fonts: `--display` (Bricolage Grotesque), `--sans` (Plus Jakarta Sans), `--hand` (Caveat). Use these rather than hardcoding values. The festive themes override these same variables in `:root[data-theme=…]` blocks — a new token should get theme values too if the themes need it. `support.html` **duplicates** the base `:root` block and the same font/CDN setup — if you rename or restyle a brand token, update both files.
- **Prices** render via `priceFmt()` / `priceFmt`-style `'₹'+n.toLocaleString('en-IN')`; star ratings via `starHTML(r)`.
- **Product images are sized per slot** with `imgW(url,w)` — it appends Sanity's `?w=<n>&auto=format` (on-the-fly resize + WebP). The Sanity loader stores a **clean base URL** in `CATALOG`/`PIMG` (no baked-in width); every render site wraps it in `imgW` at the width that slot displays (cart thumb 160, grid card 600, PDP main 1100, homepage `[data-pimg]` pins 700, trending board 640). **`COVER` is the exception** — `loadSanity()` already bakes `w=800` into it, so category/occasion covers are emitted raw (`COVER[key]`); wrapping those in `imgW` again would produce a double `?w=` and break the URL. This keeps an 80px thumbnail from downloading a full photo and caps a client's full-res phone upload. **Never emit `src="${p.img}"`/`PIMG[...]` raw — always `imgW(...)`**, and don't re-bake a width into the base URL (double `?w=` breaks it). The hero cards/mobile bg in `renderHero()` size their own `settings.hero` URLs directly.
- New interactive sections follow the pattern: add an empty container in markup → add a data array → render with a small builder that injects HTML and wires click handlers → add a `.rv` reveal animation.
